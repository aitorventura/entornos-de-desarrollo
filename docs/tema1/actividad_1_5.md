
# 🧪 Actividad 1.5: El ciclo de vida completo — mapa y análisis

!!! info "Objetivo"
    Representar las fases del ciclo de vida del software relacionando lo que entra, lo que se hace y lo que sale de cada una; y razonar cómo cambia ese ciclo según el modelo de desarrollo que se use.

---

## Parte A. Mapa del ciclo completo (a mano)

Dibuja en un folio o en papel cuadriculado un diagrama que muestre las **7 fases** del ciclo de vida con sus conexiones:

```
4.1 Análisis → 4.2 Diseño → 4.3 Implementación → 4.4 Pruebas
      → 4.5 Despliegue → 4.6 Operación → 4.7 Documentación
```

Para cada fase anota dentro del nodo:

- **¿Qué llega?** (entradas: qué necesitas tener antes de empezar)
- **¿Qué se hace?** (proceso: la actividad principal en una frase)
- **¿Qué sale?** (salidas: qué documento, código o artefacto produce)

Y entre cada par de fases, escribe en la flecha **qué se transfiere** de una a la siguiente. Por ejemplo, la flecha de Análisis → Diseño podría decir "lista de requisitos priorizados".

!!! tip "Si no sabes por dónde empezar — borrador opcional"
    Antes de dibujar, puedes usar la plantilla para rellenar la tabla de borrador con las entradas, actividad y salidas de cada fase. Una vez la tengas clara, úsala para construir el mapa. **La tabla no sustituye al mapa**: lo que hay que entregar es la foto del diagrama.

!!! tip "Cómo hacerlo bien"
    No copies los apuntes palabra por palabra. Lee la fase, cierra los apuntes y escribe con tus palabras lo que recuerdas. Luego comprueba. Lo que no recuerdes sin mirar es lo que todavía no has entendido del todo — y eso es exactamente lo que este mapa quiere detectar.

**Criterios de calidad del mapa:**

- Los 7 nodos están presentes y etiquetados correctamente.
- Cada nodo tiene al menos una entrada, una actividad y una salida identificadas.
- Las flechas entre nodos indican qué se transfiere.
- Hay al menos una flecha de **retroalimentación** (una fase que puede "volver atrás" a otra anterior) con una nota de por qué ocurre.
- El mapa es legible: letra clara, nodos diferenciados.

## Parte B. Aplica el ciclo a un proyecto real

Elige **uno** de estos tres proyectos:

- **A)** Una app móvil para que los vecinos de un edificio reserven el salón de usos múltiples.
- **B)** Un sistema web para que una clínica veterinaria gestione citas y historial de mascotas.
- **C)** Un juego sencillo de preguntas y respuestas para repasar exámenes, con varios temas.

Para el proyecto que hayas elegido, responde:

**B.1** — ¿Quiénes son los *stakeholders* (personas interesadas o afectadas) de este proyecto? Identifica al menos tres perfiles distintos y explica qué le importa a cada uno.

**B.2** — Escribe **dos historias de usuario** completas para tu proyecto, con formato *Como… quiero… para…* y al menos dos criterios de aceptación en Given/When/Then para cada una.

**B.3** — En la fase de Pruebas, ¿qué tipo de prueba usarías para verificar que una funcionalidad concreta de tu proyecto funciona? Elige una de las historias que escribiste y describe cómo sería la prueba (qué se haría, qué resultado se esperaría).

**B.4** — ¿Qué pasaría si durante la fase de Operación los usuarios detectan que la función más usada es muy lenta? Describe los pasos que seguiría el equipo, indicando a qué fase o fases del ciclo afecta.

## Parte C. Modelos de ciclo de vida — elige y justifica

Para el mismo proyecto de la Parte B, responde:

**C.1** — ¿Qué modelo de ciclo de vida usarías: cascada, incremental o ágil? Justifica tu respuesta con al menos **dos razones concretas** relacionadas con las características de ese proyecto (no vale decir "porque el ágil es mejor").

**C.2** — Un compañero propone usar **cascada** para el proyecto. ¿Cuál sería el mayor riesgo de esa decisión para este caso concreto? ¿En qué momento del proyecto podría convertirse en un problema real?

**C.3** — Si usaras un modelo **incremental**, ¿cuál sería el primer incremento que entregarías y por qué? ¿Qué funcionalidad básica debería tener para que ya aportara valor a alguien?
